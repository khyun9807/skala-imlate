## 1. 요구사항을 어떻게 읽었나

`request.md`는 A4 한 장이었다. 여기서 가장 중요한 문장은 기능 명세가 아니라 **배경**이었다.

> "22:30분부터는 기숙사 사감님도 자야하니 문이 잠긴다"
> "22:30에 넘어서 들어올 기숙이용 교육생들은 23:30에 맞춰서 한번에 들어올 것. 그 사이는 문이 잠겨있다"

이 두 줄에서 시스템의 **실패 비용**이 정해진다.

**명단에서 한 명이 빠지면 그 교육생은 밖에서 밤을 샌다.**

이게 이 프로젝트의 모든 기술 판단을 지배했다. 일반적인 CRUD 앱이라면 "등록 실패하면 다시 하면 되지"로
끝날 문제가, 여기서는 22:30 이후에는 **되돌릴 방법이 없는** 문제가 된다. 그래서:

- 데이터 유실 방지를 과하다 싶을 만큼 이중으로 걸었고
- 발송 실패를 "조용히" 두지 않는 데 집착했고
- 가용성을 위해 일관성을 일부 양보하는 선택을 반복했다

요구사항을 R1~R15로 쪼개 추적표를 만들었지만, 실제로 설계를 이끈 건 이 한 문장이었다.

### 명시되지 않은 요구를 읽어야 했던 지점

| 문서에 없던 것 | 어떻게 판단했나 |
|---|---|
| 조회 페이지 접근 제어 | "URL을 문자로 보낸다"만 있었다. 그런데 그 페이지엔 **학생 실명과 호수**가 있다. 링크가 단톡방에 한 번 새면 끝이라 HMAC 서명 토큰을 붙였다 |
| 등록 시작 시각 | 마감(22:00)만 있었다. 00:00부터 열리게 하고, **마감 후에는 "내일 00:00부터"** 를 화면에 안내했다 |
| 중복 등록 | 언급이 없었다. 학생은 새로고침하고 두 번 누른다. 유니크 제약 + 멱등 응답으로 처리 |
| 사감님이 받는 문자의 발신자 | 모르는 번호로 명단이 온다. 나중에 운영자 피드백으로 "수신 전용 + 문의처" 안내를 넣었다 |

## 2. 왜 이런 구조로 만들었나 — 핵심 설계 판단 5가지

### 2-1. WAL: Redis에 먼저 쓰고 DB에 쓴다

요구사항 원문은 `"redis에 한번(WAL처럼 DB에 기록하기 전 로깅하는 개념), DB에 한번 쓴다"` 였다.

```
① walId 생성 → ② Redis WAL 기록(PENDING) → ③ DB INSERT → ④ WAL COMMITTED
```

**핵심은 실패했을 때다.** ③이 실패하면 WAL에 PENDING이 남고, 21:50 대사(reconciliation)가
이를 발견해 DB로 복구한다. 즉 **DB 쓰기가 유실돼도 학생은 명단에 남는다.**

여기서 두 가지를 더 고민했다.

**(가) Redis가 죽으면 등록을 막을 것인가?**
막지 않기로 했다. Redis는 안전망이지 필수 경로가 아니다. Redis 장애 중에도 DB에는 정상 기록되므로
명단은 온전하다. 대신 WAL이 없어 대사에서 `dbOnly`로 잡히는데, 이건 **경고일 뿐 사고가 아니다.**
실제로 통합 테스트에서 Redis 컨테이너를 죽이고 등록이 201로 성공하는 것을 확인했다.

**(나) DB가 완전히 죽으면?**
처음 구현은 **중복 선행 조회(DB READ)가 WAL보다 앞**에 있었다. 그래서 DB가 죽으면 WAL에도
아무것도 안 남아 복구가 불가능했다. 운영자에게 "WAL이 있으니 DB가 죽어도 안전하다"고
말할 뻔했는데, 로컬 검증 가이드를 쓰던 중 이 사실이 드러났다.

순서를 바꿔 **WAL을 DB 접근보다 앞으로** 옮겼다. 이제 DB가 완전히 죽어도 등록 의도가 WAL에 남고
대사에서 복구된다. 통합 테스트 §15가 MySQL 컨테이너를 실제로 정지시켜 이를 검증한다.

### 2-2. 트랜잭션 경계를 일부러 쪼갰다

`RegistrationService.register()`에는 `@Transactional`을 걸지 않았다. 이유가 둘이다.

1. **Redis I/O 구간 동안 DB 커넥션을 붙잡지 않기 위해** — 마감 직전 200명이 몰릴 때 커넥션 고갈을 막는다
2. **유니크 충돌 후 재조회 문제** — 충돌이 난 트랜잭션은 rollback-only로 표시되어, 같은 트랜잭션 안에서
   기존 레코드를 다시 조회하면 커밋 시점에 `UnexpectedRollbackException`이 터진다

그래서 INSERT만 `REQUIRES_NEW`로 떼어냈다(`RegistrationWriter`). 이건 겪어보지 않으면
알기 어려운 함정이라 코드에 근거를 길게 남겼다.

### 2-3. 통계 이중 집계 — 복구가 만든 함정

WAL에서 복구한 등록이 **통계에 두 번 잡히는** 버그가 있었다. 12명인데 13으로 나왔다.

원인은 복구 INSERT가 `RegistrationCreatedEvent`를 다시 발행한 것. 그런데 단순히 이벤트를
안 보내면 되는 게 아니었다. **두 경우를 구분해야 했다.**

| WAL 상태 | 의미 | 통계 |
|---|---|---|
| `COMMITTED` | DB 쓰기는 성공했고 이후 행이 유실됨 → **이미 집계됨** | 재집계 안 함 |
| `PENDING`/`FAILED` | 최초 INSERT 자체가 실패 → **집계된 적 없음** | 이번에 집계 |

WAL 상태가 이 판단의 근거가 된다는 걸 알아채는 데 시간이 걸렸다. E2E 스모크 테스트가
"12명인데 13"을 잡아주지 않았다면 운영 중에도 몰랐을 버그다.

### 2-4. ALB 헬스체크의 모순

앱은 "Redis가 죽어도 등록은 계속된다"고 설계해 놓고, ALB 헬스체크는 Redis를 포함한
`/actuator/health`를 보고 있었다. 즉 **ElastiCache 장애 시 멀쩡히 동작하는 인스턴스를
로드밸런서가 서비스에서 빼버리는** 구조였다.

`db`와 `ping`만 보는 `/actuator/health/alb` 그룹을 따로 만들어 해결했다.
설계 의도와 인프라 설정이 어긋나 있었던 사례다. (나중에 ALB 자체를 걷어냈지만,
같은 원리가 nginx 헬스체크에 그대로 남아 있다)

### 2-5. Rate limiting — 두 번 다시 만든 부분

이 프로젝트에서 **가장 크게 틀렸다가 고친 부분**이다. 3장에서 따로 다룬다.

## 3. 현장을 얼마나 신경 썼나 — 공용 와이파이 사건

### 무엇이 잘못됐나

초기 rate limiter는 **IP 하나로만** 버킷을 만들었다.

```
버킷 키 = imlate:rl:{scope}:{clientIp}
등록 한도 = IP당 8회/분
```

부하 테스트는 통과했다. 200명 동시 등록에 p99 296ms, 5xx 0건. 숫자만 보면 훌륭했다.

**그런데 기숙사는 공용 와이파이다.**

NAT 뒤에서 200명이 공인 IP 하나를 공유한다. 그러면:

```
21:40  A학생 등록 → 통과 (1/8)
21:41  B학생 등록 → 통과 (2/8)
 ...
21:42  I학생 등록 → 429 차단 ❌
```

**9번째 학생부터 막힌다.** 그것도 마감 직전, 사람이 가장 몰리는 시간에. 이건 성능 문제가 아니라
**운영이 불가능한 설계 결함**이었다.

### 왜 테스트를 통과했나

부하 테스트가 요청마다 다른 `X-Forwarded-For`를 붙여 **200명을 서로 다른 IP로 시뮬레이션**했기
때문이다. `--same-ip` 옵션이 있긴 했지만 그걸 "공격 시나리오"로만 취급했다.

**기본 시나리오가 현실과 정반대였다.** 테스트가 검증한 건 존재하지 않는 환경이었다.

이 결함은 코드 리뷰로도, 테스트로도 안 잡혔다. 운영자가 **"대부분 공용 와이파이로 등록할 텐데
괜찮냐"** 고 물어서 드러났다. 현장을 아는 사람의 질문 하나가 452건의 자동 테스트보다 정확했다.

### 어떻게 고쳤나 — 축을 둘로 나눴다

| 축 | 무엇을 막나 | 한도 |
|---|---|---|
| **IP** | 한 회선에서의 대량 폭주(DDoS) | global 1200/분, register 300/분 |
| **개인** (`반\|이름\|호수` 해시) | 같은 사람의 도배 | 10/분 |

같은 와이파이의 **다른 학생**은 서로 다른 개인 버킷을 쓰므로 안 막히고, **같은 사람**이 도배하면
여전히 막힌다. 개인 식별자는 **해시해서** Redis 키에 넣는다 — 이름과 호수를 캐시에 평문으로
남기지 않기 위해서다.

부하 테스트에 **§1B "200명 전원 같은 IP"** 시나리오를 기본 실행에 넣었다. 수정 전이라면
반드시 실패했을 단언이다.

### 놓치면 결함이 되살아나는 지점

`local-fallback-permits-per-minute`도 120 → 1200으로 올렸다. 이걸 빼먹으면
**Redis가 죽는 순간 폴백 리미터가 120으로 떨어져 같은 결함이 장애 중에 부활**한다.
고친 것과 같은 논리가 폴백 경로에도 적용돼야 한다는 걸 뒤늦게 알아챘다.

## 4. 악의적 요청을 어떻게 막았나

### 방어선 구성

배포 초기에는 3단이었다가, 비용 검토 후 2단으로 줄였다.

```
[제거됨] WAF (IP당 5분 2000요청)   — nginx가 훨씬 먼저 걸려 사문화 상태였다
   ↓
nginx limit_req 10r/s burst=20     — 순간 폭주
   ↓
앱 Redis 토큰 버킷 (IP + 개인 2축) — 정교한 제어, 실제 주 방어선
```

WAF를 뺀 근거: nginx의 10r/s는 5분 환산 3000요청이지만 burst 20으로 **즉시** 429를 내므로
WAF의 2000보다 훨씬 먼저 걸린다. 즉 WAF의 rate 규칙은 도달하지 않는 코드였다. 월 $8을
사문화된 규칙에 쓰고 있었다.

### 실측 결과 (운영 환경)

| 시험 | 결과 |
|---|---|
| 등록 반복 14회 | 8건 통과 → 6건 429 (`Retry-After=6s`) |
| 순간 폭주 60건 동시 | 22건 통과 / 38건 429, **5xx 0건** |
| 조회 반복 60회 | 46건 인증실패(403) / 14건 429 |
| 위조 토큰 | **200을 받은 건 0건** |
| 차단된 요청의 DB·WAL 오염 | **0건** |
| 1분 후 | 정상 요청 200 복구 (영구 차단 아님) |

### X-Forwarded-For 위조 — 정의만 있고 구현이 없던 구멍

`RateLimitProperties.trustedProxies` 필드가 **정의만 되어 있고 아무 데서도 쓰이지 않았다.**
즉 `X-Forwarded-For`를 무조건 신뢰했다. 공격자가 요청마다 다른 XFF를 넣으면
**IP 리미터를 무한히 우회**할 수 있었다.

당시엔 nginx가 헤더를 덮어써서 실제로는 막혔지만, 구성이 한 번만 바뀌면 즉시 뚫린다.
신뢰 대역(CIDR)에서 온 요청만 XFF를 채택하도록 구현하고, 목록이 비면 `remoteAddr`만 쓰게 했다.

실측으로 확인했다 — 위조 IP 3개로 요청해도 해당 IP의 버킷이 생기지 않았다.

### 실제로 공격받고 있다

정리 중에 모르는 IP 두 개(`103.196.9.162`, `45.149.149.61`)의 rate limit 버킷을 발견했다.
공개 URL이라 **배포 몇 시간 만에 자동 스캐너가 붙은 것**이다.

이론이 아니라 실제로 필요한 방어였다.

## 5. 보안에서 신경 쓴 것

### 개인정보

명단에는 **학생 실명과 호수**가 있다. 이건 유출되면 되돌릴 수 없다.

| 조치 | 내용 |
|---|---|
| 조회 페이지 | HMAC-SHA256 서명 토큰 필수. 날짜 + 만료시각 서명, 상수시간 비교 |
| 토큰 재사용 | 다른 날짜 토큰으로 접근 시 403 |
| Redis 키 | 개인 식별자를 **해시**로만 저장 (평문 이름·호수 금지) |
| 로그 | 전화번호·이메일 **마스킹** (`010****3449`, `s***@example.com`) |
| 화면 노출 | 운영자 피드백으로 검증 결과·통계를 화면·문자에서 **전부 제거**. 기록은 유지 |
| 통계 API | 공개 → 관리자 키 보호로 전환 |

### 시크릿 관리

```
terraform.tfvars (gitignore)
   → SSM Parameter Store (SecureString)
      → EC2 부팅 시 /etc/imlate/imlate.env (root:imlate 0640)
         → systemd → Spring ${IMLATE_*}
```

**서버에 접속해 비밀번호를 타이핑할 일이 없다.** user_data에도 민감값을 넣지 않았다
(평문으로 남기 때문).

CI/CD도 **OIDC**로 붙였다. 장기 액세스 키를 리포지터리 시크릿에 두면 유출 시 회수 전까지
무기한 유효하다. OIDC는 잡마다 발급되는 단명 토큰이고, 신뢰 정책의 `sub` 조건으로
"이 리포지터리의 이 브랜치"까지 못 박는다.

### 그런데 내가 비밀값을 유출시켰다

**이 프로젝트에서 가장 뼈아픈 사고다.**

`git add -A`로 커밋하면서 terraform 저장 계획 파일(`tfoidc`)을 함께 올렸다.
**공개 저장소에** 8분간 노출됐고, 그 파일에는 상태 전체가 **평문**으로 들어 있었다.

- 알리고 API 키 / 사용자 ID
- 사감님 실제 휴대폰 번호
- DB 비밀번호, Redis AUTH 토큰, 조회 토큰 시크릿, 관리자 API 키

조치는 했다 — `force-with-lease`로 커밋을 교체하고 원격에서 사라진 것을 확인했다.
`.gitignore`에 패턴도 추가했다.

**그런데 그 패턴 추가가 실제로는 반영되지 않았고, 나중에 `tfdestroy`가 또 커밋됐다.**
같은 실수를 두 번 했다. 두 번째에는 가짜 파일을 만들어 `git check-ignore`로
패턴이 실제 동작하는지까지 확인했다.

**교훈**: "고쳤다"고 말하기 전에 **고친 것이 동작하는지** 확인해야 한다. 특히 `.gitignore`처럼
조용히 실패하는 설정은 반드시 실증해야 한다. 그리고 `git add -A`는 위험하다.

## 6. 비용을 어떻게 줄였나

### 초기 구성의 문제

첫 배포는 교과서적 구성이었다 — VPC + NAT Gateway + ALB + WAF + RDS + ElastiCache + EC2.
월 **$141**이 나왔다(문서의 $120 추정은 퍼블릭 IPv4와 CloudWatch를 빠뜨린 과소평가였다).

운영자가 **"현재 규모보다 오버스펙된 게 있냐"** 고 물었고, 실제 사용량 기준으로 다시 봤다.

| 항목 | 월 | 판정 |
|---|---|---|
| NAT Gateway | $43 | 🔴 아웃바운드가 **하루 문자 2~4건**뿐인데 시간당 요금만 냄. 전체의 31% |
| ALB | $24 | 🔴 ACM 인증서가 없어 HTTPS 종단도 못 하고, 타깃이 1대라 페일오버 이득도 없음 |
| WAF | $8 | 🔴 nginx가 먼저 걸려 rate 규칙이 사문화 |
| ElastiCache | $17.5 | 🟠 과잉이나 이미 최소 클래스 |
| RDS + 스토리지 + 백업 | $21 | 🟢 이미 최적 |

**"필요해서"가 아니라 "관행이라서" 붙어 있던 것이 $75(53%)였다.**

### 줄인 결과

`enable_alb=false`, `enable_nat_gateway=false`, `enable_waf=false`, `public_app=true`
→ **월 $67**. 변수는 남겨 두어 필요해지면 다시 켤 수 있다.

### 줄이면서 걸린 것들

**(가) 보안 그룹에 인터넷 → EC2 규칙이 아예 없었다.**
app SG의 인바운드가 전부 "ALB SG 참조"였다. ALB를 끄면 **접속 자체가 불가능**해진다.
`enable_alb=false`라는 변수는 있는데 그것만 켜면 서비스가 죽는 구조였다.
`enable_direct_ingress`를 추가하고, ALB를 쓸 때는 켜지지 않도록 배선했다(ALB 우회 방지).

**(나) 알리고 화이트리스트 IP가 바뀐다.**
NAT를 없애면 아웃바운드 IP가 NAT EIP → EC2 EIP로 바뀐다. 이걸 놓치면
**22:10에 문자만 조용히 실패**한다. 실제로 재배포할 때마다 IP가 바뀌어 두 번 겪었다.
`terraform output aligo_whitelist_ip`로 바로 확인되게 만들었다.

### 백업 보존일을 줄이지 않은 이유

흔한 절감 후보지만 **RDS 자동 백업은 할당 스토리지(20GiB)까지 무료**다.
실 DB가 수십 MB라 7일 → 1일로 줄여도 **절감액 $0**이고 복구 폭만 잃는다.
"줄일 수 있을 것 같지만 실제로는 안 되는 것"을 따로 정리해 문서에 남겼다.

## 7. 실제 배포에서만 드러난 결함 8건

로컬 테스트 452건을 통과한 코드가 실제 AWS에서 8번 깨졌다.
**전부 로컬에서는 절대 재현할 수 없는 것들이었다.**

| # | 증상 | 원인 |
|---|---|---|
| 1 | `terraform init` 자체가 실패 | HCL은 줄 끝 `+`로 식을 이어갈 수 없다. 이 한 줄 때문에 terraform이 전혀 동작하지 않았다 |
| 2 | ElastiCache `Invalid AuthToken` | 허용 특수문자가 `! & # $ ^ < > -` 8개뿐인데 `% * ( ) _ = +`를 썼다. 주석에는 "`/ " @`만 불가"라 적혀 있었다 |
| 3 | IAM 역할 `ValidationError` | **description에 한글을 쓸 수 없다** (ASCII/Latin-1만 허용) |
| 4 | `-target`이 인프라 전체를 생성 | OIDC 모듈이 `module.ec2`를 참조해 의존성이 줄줄이 딸려왔다. "OIDC만 따로 만들 수 있다"고 안내해 놓고 내가 그걸 불가능하게 만들었다 |
| 5 | GitHub Actions `AssumeRole` 거부 | GitHub이 `repo:owner@<ID>/repo@<ID>:...` 형식으로 sub를 보낸다(immutable ID). CloudTrail에서 실제 거부된 sub를 봐야 알 수 있었다 |
| 6 | `deploy.sh`가 Windows에서 실패 | Git Bash 경로(`/c/Users/...`)를 Windows `aws.exe`가 못 읽는다 |
| 7 | 프론트 화면 404 | ALB가 8080(Spring 직결)을 봐서 nginx가 서빙하는 정적 파일 경로를 안 탔다 |
| 8 | 타깃 그룹 교체 실패 | `create_before_destroy` + 고정 이름 조합 → 이름 충돌 |

**5번이 가장 어려웠다.** 신뢰 정책도, 워크플로 설정도, 저장소 이름도 전부 맞았는데 거부됐다.
CloudTrail에서 실제 토큰의 `sub`를 꺼내 보고서야 GitHub이 형식을 바꿨다는 걸 알았다.
추측으로는 절대 못 잡았을 문제다.

**교훈**: 인프라 코드는 실제로 `apply` 해보기 전까지 검증된 게 아니다. `validate`는
문법만 본다. 그리고 외부 서비스(GitHub, AWS, 알리고)의 계약은 조용히 바뀐다.

## 8. 테스트가 거짓말한 순간들

가장 불편했던 발견은 **테스트 자체가 틀렸던** 경우들이다.

### 8-1. 항상 통과하는 가짜 단언

```js
check('대사에서 DB-only 로 보고됨', /MISMATCH|CONSISTENT/.test(status) || true)
//                                                                  ^^^^^^^ 
```

`|| true` 때문에 **무조건 통과**했다. 통과 표시가 나오지만 아무것도 검증하지 않는다.
실제 대사 결과를 확인하도록 교체했다.

### 8-2. 자기 전제를 검증 못 하는 테스트

부하 테스트가 rate limit 한도를 `/actuator/env`에서 읽으려 했는데, Spring이 값을
`******`로 마스킹한다. 그래서 **잘못된 폴백값(5)으로 판단**하고 경고를 냈다.
실제 앱은 10을 쓰고 있었다.

설정을 열어 마스킹을 푸는 건 DB 비밀번호까지 노출시킨다. 대신 **`X-RateLimit-Limit` 응답 헤더**에서
실제 적용값을 읽도록 바꿨다. 런타임 결정값이라 더 정확하고 부작용도 없다.

### 8-3. 현실과 반대인 기본 시나리오

3장의 공용 와이파이 건. **테스트가 검증한 환경이 실제 운영 환경과 정반대**였다.

### 8-4. 테스트를 고치다 만든 새 버그

한도 측정용 프로브가 **실제 등록을 하나 생성**해서 이후 건수 단언이 전부 어긋났다.
검증 규칙을 일부러 어긴 이름(`LimitProbe!!`)을 써서, 인터셉터는 통과하되 컨트롤러에서
400으로 거부되게 만들어 비파괴적으로 바꿨다.

> **정리**: 테스트는 코드만큼 틀린다. "통과했다"가 "검증됐다"를 뜻하지 않는다.
> 특히 단언이 조용히 무력화되는 패턴(`|| true`, 읽기 실패 시 경고 강등, 잘못된 폴백값)을 경계해야 한다.

## 9. 운영자의 니즈를 어떻게 반영했나

요구사항 문서에 없던, 대화 중에 나온 피드백들이다.

| 피드백 | 무엇을 읽었나 | 조치 |
|---|---|---|
| "오버스펙인 NAT/ALB 쓰지 말자" | 학생 프로젝트에 월 $141은 부담 | 월 $67로 (6장) |
| "필요한 정보만 보이게" | 화면이 개발자용으로 만들어져 있었다 | 등록 인원 수 등 제거 |
| "검증 결과·복구·통계는 안 보이게. 뒤에서 기록만" | **사감님은 DB/WAL 카운트를 알 필요가 없다.** 시스템 내부 사정을 사용자에게 보여주고 있었다 | 화면·문자·메일에서 제거. 대사와 집계는 그대로 수행하고 로그·관리 API로만 확인 |
| "URL이 고정되어야 한다" | 재배포마다 주소가 바뀌면 사감님이 헷갈린다 | 도메인 + EIP 고정 + HTTPS |
| "22:00 → 21:45로, 발송도 21:50" | 현장 운영 편의 | 설정만 변경(하드코딩이 없어 가능했다) |
| "수신 전용 번호라고 표시하고 문의처 추가" | **모르는 번호로 명단이 오는데 답장도 안 된다.** 사감님 입장을 생각한 요구 | 문자·메일에 안내 추가, 문의처는 설정으로 분리 |
| "같은 내용 반복 등록하면 계속 등록돼?" | 실사용에서 반드시 생기는 상황 | 이미 멱등이었고, 5회 재제출 → DB 1건을 실증 |
| "공용 와이파이인데 괜찮아?" | **현장을 아는 사람만 할 수 있는 질문** | 3장 |

### 특히 잘 읽어야 했던 것

**"검증 결과는 안 보이게, 뒤에서는 기록"** — 이건 단순히 "지워달라"가 아니었다.
대사를 **하지 말라는 게 아니라 보여주지 말라**는 요구다. 그래서:

- `GET /lookup` 응답에서 `verification`/`stats` 제거
- 그러나 `ReconciliationService.inspect()` 호출은 **유지**하고 결과를 로그로 남김
- 운영자용 `GET /admin/reconciliation` 신설 — 확인 수단이 사라지면 안 되니까
- 통합 테스트에 **반전 단언** 추가 — 나중에 다시 노출되면 테스트가 실패하도록

"기록은 그대로, 노출만 줄인다"를 원칙으로 못 박고 양쪽을 다 검증했다.

## 10. 운영 투입 전에 걱정한 것

기능이 다 돌아간다고 운영 준비가 된 건 아니었다. 실제 운영 직전 위험 평가에서
**세 가지 구멍**이 나왔다.

### 10-1. 장애가 나도 아무도 모른다

CloudWatch 알람이 **0개**였다. EC2 1대(단일 AZ)에 앱·nginx가 다 올라가 있는데,
21:50 직전에 인스턴스가 죽으면 발송이 통째로 실패하고 **다음 날 사감님이 "명단 안 왔다"고
할 때야 안다.** `systemd Restart=always`는 프로세스 재시작만 커버한다.

→ 알람 7종 + SNS 추가.

**가장 중요한 건 하트비트 알람이다.** 앱이 발송 후 CloudWatch 지표를 올리고,
**21:50에 그 지표가 오지 않으면** 알람이 울린다. "아무 일도 일어나지 않은 것"을
밖에서 감지하는 유일한 수단이다. 통금 22:30 전에 알아챌 수 있게 배치했다.

### 10-2. 발송 실패가 조용하다

실제로 운영 중 두 번 겪었다 — 알리고 IP 미등록, SES 미검증. 둘 다 DB에 기록만 되고
아무도 알려주지 않았다. 관리 API를 직접 조회해서야 알았다.

→ 실패 시 운영자에게 **원인 요약 + 조치 힌트** 통보. 수신처를 사감 채널과 설정 경로부터
분리했다(알림이 사감님께 잘못 가면 안 된다).

### 10-3. 알리고 잔액 소진도 조용하다

→ 임계값 미만이면 경고.

### 하트비트 구현에서 잡은 연결 오류

두 담당이 각자 만든 것이 **서로 연결되지 않는** 상태였다.

- 앱은 로그에 마커만 남김
- 알람은 CloudWatch **지표**를 봄
- 둘을 잇는 지표 필터가 없음 → **알람이 영구 ALARM**

로그 필터를 추가하는 대신 CloudWatch SDK로 직접 발행하도록 바꿨다.
로그 그룹은 CW 에이전트가 만들어 terraform 소유가 아니고, 평문 로그로는 차원을 만들 수 없기 때문이다.

그리고 **차원까지 어긋나 있었다.** 앱은 `{Environment, Kind}`를 붙이는데 알람은 차원 없이 봤다.
CloudWatch는 **차원이 다르면 아예 다른 지표**라 영원히 데이터를 못 찾는다.
배선을 맞추고 `IMLATE_ENV`도 명시 주입해 양쪽이 갈라질 여지를 없앴다.

리허설 발송 때 지표가 `{Kind=DISPATCH, Environment=prod}`로 정확히 올라간 것을 확인했다.

## 12. 남은 위험과 한계

운영 중인 시스템의 **현재 한계**를 정직하게 적는다.

| 위험 | 현재 상태 | 완화 |
|---|---|---|
| **단일 인스턴스·단일 AZ** | EC2 1대에 앱·nginx가 전부 | 알람으로 감지는 되지만 **자동 복구는 없다.** 사람이 조치해야 한다 |
| **RDS Single-AZ** | 장애 시 복구에 시간 소요 | 200명 규모에 Multi-AZ(+$18/월)는 과하다고 판단 |
| **SES 샌드박스** | 수신자 검증 필수 | 사감 이메일이 바뀌면 재검증 필요. 하루 200통 한도는 충분 |
| **메일 배달률** | 발신이 naver 주소인데 SES로 나감 | SPF/DKIM이 정렬되지 않아 스팸함 가능성. 학교 도메인 확보 시 개선 |
| **사감 이메일이 운영자 주소** | 의도적 선택 | 사감님은 **문자만** 받는다. 메일은 운영자 확인용 |
| **알리고 IP 의존** | 재배포 시 EIP가 바뀌면 문자 실패 | `terraform output aligo_whitelist_ip`로 확인. 자동화되지 않음 |
| **조회 토큰 48시간** | 링크 유출 시 그동안 열람 가능 | 필요하면 `token-ttl-hours`를 줄일 수 있음 |

## 13. 돌아보며

### 숫자로 본 과정

```
요구사항 1장  →  231개 파일 · 커밋 11개 · 검증 452건 · 실배포 결함 8건
```

### 가장 값졌던 것

**운영자의 질문 하나가 452건의 자동 테스트보다 정확했다.**

"공용 와이파이인데 괜찮아?" — 이 질문이 없었다면 마감 직전에 학생들이 무더기로 차단되는
사고를 실제로 겪고서야 알았을 것이다. 코드도 테스트도 CI도 이 결함을 못 잡았다.
**도메인을 아는 사람만 물을 수 있는 질문**이었다.

### 반복해서 확인된 것

1. **로컬 통과 ≠ 동작함.** 실제 배포에서 8건이 깨졌고 전부 로컬 재현 불가였다.
2. **테스트도 틀린다.** 가짜 단언, 잘못된 전제, 현실과 반대인 시나리오를 직접 만들었다.
3. **조용한 실패가 가장 위험하다.** 이 프로젝트에서 고친 것의 절반은 "실패했는데 아무도 모르는"
   상황을 "실패하면 알게 되는" 상황으로 바꾸는 작업이었다.
4. **설계 의도와 설정은 어긋난다.** "Redis 없이도 동작"으로 만들어 놓고 헬스체크는 Redis를 봤고,
   "OIDC만 따로 만들 수 있다"고 해놓고 의존성을 걸었다. 의도를 코드로 강제하지 않으면 갈라진다.

### 이 시스템이 지키는 것

매일 21:45에 마감하고, 21:50에 사감님 두 분께 명단을 보낸다.
그 문자 하나가 제때 가지 않으면 누군가는 22:30에 잠긴 문 앞에 서 있게 된다.

**기술적으로 흥미로운 문제라서가 아니라, 그 한 명이 밖에서 밤을 새우지 않게 하려고
이 모든 걸 했다.**
